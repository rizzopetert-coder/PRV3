## Gemini's review — verified findings and corrections

A full verification pass was run against Gemini's MemPalace-retirement review, same standard as every other Gemini review this session (check every citable claim against live source before treating anything as established). Full detail of all seven items checked is in this session's own transcript; the four that materially change what should be written into a retirement plan are captured here so they aren't lost.

### Item 1 — the "client-side filtering bug" claim is inverted, not fabricated

Gemini characterized a "client-side filtering bug (`metadata.type == 'diary'`)" as something caught during the pilot. A real bug was genuinely found and fixed during the pilot — but it's the opposite of Gemini's description. Confirmed directly in both `C:\mem0_trial_venv\prv3_diary.py` (lines 113-120) and `prompts/mem0-pilot-continuity-layer.md` ("A real bug found and fixed before trusting it with real content"): the actual bug was a **server-side nested filter** (`filters={"user_id": ..., "AND": [{"metadata.type": "diary"}]}`) that this Qdrant-backed Mem0 version silently doesn't support — it matched zero results with no error raised. The fix was **client-side filtering** (`metadata.type == "diary"`), which is the working, correct solution, not the bug. **Do not carry Gemini's inverted framing forward** — if this incident is referenced again, describe it as "an unsupported server-side nested filter, fixed via client-side filtering," not "a client-side filtering bug."

### Item 2 — `hnsw:sync_threshold` / `-32000` errors do not apply to this issue; don't reuse this framing

Gemini attributed MemPalace's chromadb crash specifically to `hnsw:sync_threshold` blockage and `-32000` errors. Checked against the actual, current root-cause record — `prompts/mempalace-rootcause-hnsw-desync-investigation-20260825.md` — in full: **zero mention of either term.** The real, current, still-unproven finding is orphaned HNSW slots (6,005 in `mempalace_drawers` vs. 122 in a healthy control, a real quantified 7.9%-vs-3.9% differential), explicitly stated in that document as *"not proven; this remains one level more precise, not a confirmed root cause."* `hnsw:sync_threshold` is real terminology from this project, but it belongs to a **separate, already-closed** MemPalace issue (the `mempalace mine` silent-non-persistence bug, root-caused and fixed earlier this session via a per-process sync-threshold counter reset) — a different mechanism from the segfault/"Connection closed" issue this retirement review is actually about. **Do not reuse Gemini's `sync_threshold`/`-32000` framing anywhere in retirement documentation** — it either conflates two distinct MemPalace problems or invents precision that was never established for this one.

### Item 5 — MOB Section 12 is explicitly LOCKED; retirement is not a `CLAUDE.md`-only edit

`tools/_mob.txt` Section 12, **"MemPalace Integration — Locked"** (confirmed at the file's real current line 1007, verified against the live section-header list, no drift from what Gemini referenced), documents the wing/rooms/drawer-count/mine-command/diary convention as locked protocol — Wing `prv3`, Rooms `documents/engine/prompts/scripts/general`, `mempalace mine` "runs at every session close," diary "write at close, read at open." **Retirement requires formally unlocking and rewriting this section**, not just editing `CLAUDE.md`'s protocol steps — leaving Section 12 as-is while changing `CLAUDE.md` would leave the MOB's own locked-decisions record contradicting the actual protocol.

### Item 7 — real concurrent-write collision risk, not hypothetical, needs a documented mitigation before adoption

`prv3_diary.py`'s `STORE_PATH` (`C:/mem0_trial_venv/qdrant_data`) and `migrate_mempalace.py`'s `QDRANT_PATH` (same literal string, confirmed at that script's line 49) point at the **identical on-disk Qdrant directory** — different collection names (`prv3_trial` vs. `mempalace_migration`) within the same store. Confirmed directly: `qdrant_data/.lock` exists on disk. Qdrant's local/embedded backend is single-process by design and uses this file as an advisory lock. **This is not a theoretical risk — the just-completed migration already ran a ~26.5-hour long-running process against this exact path.** Had `prv3_diary.py write` been invoked during that window, it would have collided against the same lock rather than safely interleaving. Gemini's proposed safeguard assumes single-agent execution only and does not account for this. **Before adoption is finalized, this needs a documented mitigation** — most likely a note in whatever replaces `CLAUDE.md`'s protocol steps (step 2 of the plan above), flagging that any future long-running background job touching this path (a future migration, a bulk evaluation run, anything else) must not run concurrently with a live session's diary write/read, or a real fix (separate collections in separate on-disk paths, or a proper server-mode Qdrant deployment) needs to be scoped instead.
