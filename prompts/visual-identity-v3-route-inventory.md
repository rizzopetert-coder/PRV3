# Visual Identity v3 — Route Inventory (report only, no code changes)

Produced 2026-08-22, same session as Task 1 (Dark/Neutral token wiring) and Task 3 (NavBar fix). Every claim below is sourced from a direct read of the route's own `page.tsx` and/or a direct grep across `web/app` and `web/components` — reachability in particular is grep-verified against real `href=` values, not assumed from route naming or MOB history. Where MOB history and a direct source read disagreed, the source read wins and the discrepancy is called out.

This is inventory only. No rollout plan, no mounting decision, no usage recommendation — that's explicitly out of scope, reserved for a future Gemini-gated architecture review built from these findings.

## Cross-cutting findings (apply to every route, not repeated per row)

1. **Every route can theoretically render in Dark or Neutral today, without `ThemeSwitcher` ever being mounted.** `web/app/layout.tsx` carries a blocking anti-flash script (OD-07 Stage 1) that reads `localStorage["prv3-theme"]` and sets `data-theme` on `<html>` before first paint, on every route, unconditionally. No live page can currently *write* that key (`ThemeSwitcher` is dormant, mounted nowhere — confirmed, see below), but a returning visitor from before the v1 rollback (commit `b8860b5`) could still be carrying a stale `"dark"` or `"neutral"` value and would see every route's `--field`/`--ink`/`--oxide` set (and, after Task 1, the new Dark/Neutral v3 colors too) applied site-wide. Genuinely live, genuinely edge-case, worth knowing about before anyone assumes "Warm is the only theme anyone will ever actually see."

2. **The v2 `--oxide`/`--urgency` token layer has zero live consumers anywhere in the app today, except the new `/about/services` v3 pilot.** Checked via direct grep across all of `web/components` for `var(--oxide`, `var(--urgency`, `text-oxide`, `bg-oxide`, `text-urgency`, `bg-urgency` — the only hit is `ThemeSwitcher.tsx` itself (not mounted). This confirms and extends this session's own Quarterly Step-Back finding (MOB v4.223) that "the v2 token layer had ZERO live consumption anywhere before this session" — it's still true after this session too, for every surface except `/about/services`.

3. **Every severity/diagnostic-adjacent surface in the app renders on legacy v1 tokens (`--color-charcoal`, `--color-slate`, `--color-rust`), not v2 or v3.** This corrects an assumption I was carrying into this task from MOB history predating the OD-07 rollback. `ConstellationField.tsx` — the shared component behind the homepage's ambient shape *and* the live results-page shape in `PrivateOutput` — is direct-read confirmed to use `var(--color-rust)` exclusively at genuine Endemic severity and `var(--color-slate)` otherwise, both v1 Session-58 tokens, enforced structurally in code (its own header comment: ambient mode is structurally incapable of ever referencing `--color-rust`). `PrivateOutput.tsx`, `CondensedOutput.tsx`, and `ShareableOutput.tsx` all use plain `text-charcoal`/`gray-*` UI chrome — no `--oxide`/`--urgency` anywhere. **Net effect: the one live v3 surface (`/about/services`) has zero severity-content adjacency, and every surface that does carry severity content is untouched by v2 or v3.** A future v3 rollout onto any severity-adjacent surface is genuinely new territory, not an extension of existing precedent — and `--urgency`/rust's Endemic-exclusivity constraint has never yet had to coexist with the v3 palette on the same page.

4. **`--color-slate` is ambiguous by name across two live systems, resolved by which syntax a page uses.** `globals.css`'s own comment explains this: the Session-58 v1 palette's `--color-slate` (`#4A6B85`, mapped as a real Tailwind utility) and OD-07's v2 `--slate` (`#5C6B66`/`#8FA39C`/`#7A7E82` per theme, deliberately *not* mapped to `--color-slate` to avoid the collision — must be consumed via `text-[color:var(--slate)]` arbitrary-value syntax instead). `book/toc/page.tsx`'s signature-tag pills use the bare `border-slate`/`bg-slate`/`text-slate` utility classes, which resolve to v1's fixed `#4A6B85`, not v2's per-theme value — confirmed by which syntax is actually in the source, not assumed from the name.

## `ThemeSwitcher.tsx` — plausible mount points (not mounted anywhere today)

`ThemeSwitcher` applies `data-theme` to `document.documentElement` (the `<html>` tag) directly, not to any scoped subtree. **This means mount location never changes what a toggle affects — flipping to Dark or Neutral always re-themes the entire site globally, every route, regardless of where the control itself lives.** The only thing mount location changes is *who can discover and use the control*, not its blast radius. Concretely:

| Mount point | What it would change for a user |
|---|---|
| **`NavBar.tsx`** (global, every route) | Control visible and usable from anywhere in the app, all the time. Highest discoverability, but a persistent UI element on every single page, including the diagnostic flow itself, where an extra top-bar control could compete for attention during a focused question sequence. |
| **`app/layout.tsx` footer** (if one existed — none currently does) | Same global reach as NavBar, lower visual priority (users have to scroll or look down), less likely to be noticed or used by a first-time visitor. |
| **`/about` page** (once it's no longer an orphaned stub — see Task 4) | Scoped *discoverability* to one page, but the effect on selection is still global (leaves `/about` and persists everywhere via localStorage). Fits a "site preferences" mental model without cluttering the primary nav. |
| **A dedicated `/settings` or `/preferences` route** (doesn't exist today) | Same global-effect-but-scoped-discovery pattern as `/about`, cleaner separation of concerns, but adds a net-new route and a net-new nav entry to reach it. |
| **Dev-only surface** (e.g. alongside `/dev/diagnostic-fixture`) | Effectively private — only reachable outside Production, useful for internal QA/screenshotting across themes but invisible to any real visitor, meaning Dark/Neutral would stay permanently unseen by real users even after being wired (Task 1) and mounted. |

No option above is proposed, recommended, or decided here — this is the raw set of where the component could physically go and what changes (or doesn't) per option, for a future review to weigh.

## Follow-up (2026-08-22) — is `ShareableOutput.tsx`'s plain-text severity rendering deliberate or an oversight?

The original inventory above (the `/share/[id]` row and cross-cutting finding 3) established that `ShareableOutput.tsx` renders `payload.severity` as plain uncolored text, using none of the `severityAccentTokens()`/rust/slate machinery its three siblings (`ConstellationField`, `PrivateOutput`, `CondensedOutput`) all use. Investigated whether that was ever an explicit choice. **Findings only — `ShareableOutput.tsx` was not touched.**

**Timeline, via `git log`/`git blame` on the exact severity-badge span (Block 2, `<span className="text-[11px] bg-gray-100 border border-gray-200 text-gray-500 ...">{payload.severity}</span>`):**

- Authored 2026-06-14 (commit `3bc849c`, "S43: PrivateOutput + ShareableOutput rendering pass") — a plain gray badge from day one.
- `severityAccentTokens()` did not exist yet at that point — it was created over five weeks later, 2026-07-21 (commit `c9e63d9`, "Add live-mode ConstellationField for results-page use"). The color-coding mechanism this question asks about literally did not exist when this line was written, so its absence here cannot have been a deliberate choice to skip it at the time.
- One visual-identity sweep did touch this file in between (`0e13fa4`, 2026-07-05, "implement locked visual identity tokens across web layer") — but it only converted other `gray-900` spans to `text-charcoal` and explicitly left this exact badge untouched. That commit's own message states "Rust defined, not applied" anywhere in the codebase at that point, consistent with severity-color-coding being globally unaddressed then, not a `ShareableOutput`-specific call.
- Two more commits touched this file **after** `severityAccentTokens()` existed — `2a0bc77` (2026-07-28, threading the headline field through) and `e5f6592` (2026-08-05, headcount-precision copy). Neither touched or mentioned the severity badge; both are narrow, unrelated feature additions with no styling scope. Nobody has revisited this specific span since the accent-color mechanism came into existence.
- No comment anywhere in the file explains or justifies the plain rendering.

**Documentation search:** grepped all of `prompts/` for `ShareableOutput`/`/share/[id]` (15 files) and for "clinical"/"distraction-free" phrasing (8 files, all unrelated — every "clinical" hit across the whole repo refers to Pete's clinical judgment/expertise, a state's pre-rename "clinical name," or the synthesis engine's clinical-boundary content rule, never to UI/visual design). **No prior project document, anywhere, ever articulates a "clinical and distraction-free" design rationale for `/share/[id]` or `ShareableOutput.tsx`.** The closest related document, `prompts/visualize-your-data-severity-comparison-concept.md`, is about a *different, not-yet-built* feature (a new per-state severity comparison section) and explicitly treats color-coding as the plan for that new section ("a color-coded tier badge," with only the *implementation* choice — reuse `severityAccentTokens()` or build a new one — left open). The MOB's own "Visualize Your Data Phase 2" decision (2026-08-20/21) calls for a future "tier-only, stripped-down" shareable surface, but that decision is about omitting the *magnitude bar*, not about color, and it governs a section that doesn't exist yet — it doesn't speak to the existing Block 2 badge this question is about.

**Conclusion: undocumented/accidental, not deliberate.** This reads as a straightforward timing artifact — the badge was written before the tool to color it existed, and nothing has revisited it since, not a considered "keep `/share/[id]` distraction-free" decision. Gemini's "clinical and distraction-free" framing does not trace to any citable prior project record; it reads as Gemini's own post-hoc rationalization for an observed pattern, not a citation of real design intent.

**Open question for Pete, not decided here:** bring `ShareableOutput.tsx`'s primary severity badge in line with its siblings (reuse `severityAccentTokens()`, same as `PrivateOutput`/`CondensedOutput` already do), or leave it as-is now that a *plausible* distraction-free rationale exists even if it wasn't the original reason. Either is defensible — this is a judgment call, not a bug fix, and no rendering change was made in this pass.
