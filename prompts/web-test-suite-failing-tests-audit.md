## Why this matters, stated precisely (not overstated)

**No live risk today.** The functions these tests exercise (`spliceDistinguishers`, `coreQuestionPosition`, `TOTAL_CORE_QUESTIONS`) are confirmed, independently, to behave correctly against the real, current, 42-question library — verified directly, not inferred from the tests passing or failing. Checkpoint splicing and severity follow-on splicing in the live `session/answer/route.ts` are not affected by this staleness at all; the test suite's hardcoded expectations are wrong, not the production code they're checking.

**Real, if lower-severity, cost:** with these 6 tests failing on a known, expected, hardcoded-length mismatch, they currently provide **no actual regression protection** for the logic they're meant to guard — a future real bug in `spliceDistinguishers()`'s positional/compounding logic could land silently, because these tests already fail for an unrelated, known reason and nobody would notice a *new* failure mixed in with 6 *expected* ones. This is the concrete argument for eventually updating the hardcoded lengths (not decided or actioned here, per the explicit instruction) — not because anything is currently broken, but because the safety net these tests exist to provide is currently not functioning as one.
